# Echo — end-to-end audit (2026-08-06)

**Purpose.** Find the best improvements across the whole system: app, cloud server, data, tests,
docs, and operations. This is an audit, not a change set — nothing in the codebase was modified.

**Method.** Six parallel auditors, one per subsystem (audio capture, transcription pipeline, cloud
path both sides of the wire, data layer + summaries, UI/build/security, tests + docs), each reading
their files in full. On top of that: a triage of the 12 findings the queue-hardening sprint logged
but never verified, and a repo/operations sweep. The phone was offline for the whole audit, so
anything that needs the device is listed in §J rather than claimed.

**Severity scale.** P0 = data loss, crash, security/privacy exposure, or recording silently stops.
P1 = correctness bug, stuck queue, serious battery/cost. P2 = robustness, performance,
maintainability. P3 = polish.

---

## A. Executive summary

Six parallel auditors read every first-party file in full (app, server, tests, docs, build), the 12
unverified sprint findings were triaged against current code, and the repo/ops surface was swept. Net:
**~95 filed findings deduplicating to roughly seventy distinct improvements**, fourteen of them found
independently by two or more auditors — high-confidence by convergence.

**The eight that matter most:**

1. **A silenced microphone is undetected** (§D, P0). On Android 10+ a phone call delivers zeros, not
   errors; Echo records them as "Listening", the VAD calls them silence, and the WAV is deleted. A
   2-hour call becomes unrecoverable nothing. The restart path then re-arms the lie. One callback API +
   a zero-buffer counter fixes it.
2. **The keep-audio pressure latch silently destroys transcript quality** (§G+§E, P1, found twice
   independently). The 1 GB retention cap counts audio the relief valve can never release; once crossed
   (~9 h of speech with keep-audio on), every server blip grinds chunks through the 0.00-recall engine —
   and marks them unredoable. The trigger and the relief measure different sets.
3. **The silence gate deletes short utterances in long chunks** (§D, P1). "Silent" is 2 % *of chunk
   length*: one 5-second sentence in a 10-minute chunk is below the bar, and first-pass chunks have no
   wordCount protection. Scales up exactly when the app moves to its spec'd 10-minute chunks.
4. **The daily summary lies about backlogged days, and missed days are never summarised** (§G, P1×2).
   The `provisional` column and `unsettledBetween` query exist for exactly this and are wired to
   nothing; a cold-server day gets "no speech detected / 0 words", final forever. A 23:00 that passes
   powered-off is silently skipped. The 23:00–24:00 hour appears in no summary, ever.
5. **Recording can die silently in at least three ways** (§D+§H, P1s, found twice each): a reused
   service instance runs with `stopping = true` (retry and monitors permanently dead, notification still
   "Listening"); foreground-promotion failure calls `stopSelf()` with no signal; and nothing anywhere
   posts the existing "not listening — tap to resume" notification except the boot path.
6. **The cloud path has two self-inflicted permanent stalls**: a bad-key halt survives the user fixing
   the key (the halt-clearer is behind the halt's own gate, §F P1), and a service restart steals the
   live worker's claim (three quick toggles retire a healthy chunk, §E P1). Plus: uploads run on metered
   data with no opt-in, and the server logs full transcript text to Cloud Logging (§F, P1s).
7. **The test suite cannot see the most dangerous regressions** (§I, P0×3). Settle atomicity, all DAO
   SQL, and the migration have no real-database coverage on any runtime; two of the four data-loss fixes
   at HEAD are untested and one fake still models the pre-fix bug; the five instrumented suites remain
   an uncontained wipe-the-phone footgun. No CI runs the 135 green tests that do exist.
8. **Operations: the three most valuable commits are unpushed, and the deployed server's security
   hardening exists only as an uncommitted diff** (§B, P1s) — rebuilding from committed state
   reproduces the HF_TOKEN-in-image leak. Room schema export is off, so the schema v3 that several
   fixes need would be written blind.

**What is solid — and it is a lot:** the lease/claim design survives adversarial reading (transactional
claim, lease-conditional writes, rollback on lease loss, crash-loop bounded); the audioHold
null-is-never-permission model is carried consistently everywhere; chunk rotation is gapless by
construction; WAV crash-safety is genuinely good; backup posture is airtight (transcripts can never leave
via Google backup); BatchProtocol matches the server byte for byte (every field diffed); payload math
clears every limit by construction; no secret leaks in logs, git, or UI; the cloud piece machine's test
coverage is exemplary *for the parts it covers*; and the docs' enforced/not-enforced honesty is the right
genre — they just describe last week's code.

The ordered plan is §K. Everything above cites file:line evidence in its section.

- Where: `app/build.gradle.kts` / missing `app/schemas/`
- Evidence: no `schemas/` directory exists and no schema JSON is tracked in git.
- Problem: MIGRATION_1_2 was written against a live device DB and verified by hand. Without

- Problem: 135 JVM-safe unit tests exist but only run when someone remembers. The instrumented

  device, no instrumented tests.

**Solid, for the record:** `.gitignore` is thorough (local.properties, keystores, `*.bin` weights
all excluded; nothing secret-ish tracked); whisper.cpp is a proper submodule pinned at `306c88f`
with a clean working tree, so a fresh `git clone --recursive` is reproducible.

## D. Audio capture chain

### [P0][data loss] A silenced microphone is undetected — calls get recorded as zeros, then deleted as "silence"
- Where: `AudioChunker.kt:176–201` (readerLoop), `RecordingService.kt:211–217`; SYSTEM_DESIGN.md §6 and the
  module table promise a `MicWatchdog`/`AudioRecordingCallback` that **does not exist anywhere in the source**.
- Problem: on Android 10+ concurrent-capture policy, a phone call, the assistant, or another recorder does
  not make `read()` error — the framework keeps delivering full buffers of **zeros** (`isClientSilenced`).
  Any positive read is treated as good audio. Worse, if a hard error does fire, the 1 s restart succeeds
  (silenced), `isRunning == true`, `restartAttempt = 0`, and the notification flips back to "Listening"
  for the whole call. The zero-filled chunks then fail VAD → `commitSilent` → **WAV deleted**. A 2-hour
  call is unrecoverable and presented as silence. The same mechanism fires after an OOM-kill restart with
  the app in background (while-in-use mic restriction silences the new session) — recording can die
  silently overnight.
- Improvement: minSdk is 29, so `AudioManager.registerAudioRecordingCallback` +
  `AudioRecordingConfiguration.isClientSilenced()` is always available — route "silenced" into the existing
  `onCaptureLost` path (which already pauses, notifies honestly, backs off). Belt-and-braces in
  `readerLoop`: ~5 s of consecutive bitwise-zero buffers → `onCaptureLost("microphone silenced")`; don't
  reset backoff/"Listening" until a non-silenced buffer arrives; also count `n == 0` returns (currently a
  potential tight spin at `MAX_PRIORITY`).

### [P1][robustness] `stopping`/`monitorsStarted` are never reset — a reused service instance is a zombie that says "Listening" forever
- Where: `RecordingService.kt:60–64, 224–242, 244–302, 304–315`. Android reuses the service instance when a
  start intent races a pending `stopSelf()` (Stop from the notification then Start in the app; or the 23:00
  summary-only wake racing a user start). The new session runs with `stopping = true`: disk monitoring dead,
  notification refresh dead, and `scheduleRestart()` early-returns **before** `setRecording(false)` — so on
  the next mic loss nothing retries, state stays `recording = true`, notification says "Listening",
  permanently. Fix: reset `stopping`/`diskPaused`/`restartAttempt` in `onStartCommand` for START, and hold
  monitor `Job`s that `shutdown()` cancels and start relaunches.

### [P1][transcript quality] The percentile-floor VAD collapses on continuous noise — the 88 %-voiced chunk, at the source (open task #11)
- Where: `VoiceActivityDetector.kt:25–49, 71–75, 88–152`; `TranscriptionPipeline.kt:374–392`.
- Problem: `noiseFloor = sorted[20th pctile]` assumes ≥20 % of frames are noise-only; in modulated
  continuous noise (TV, traffic, babble) the percentile lands in a trough and most frames clear
  `2.5×` it — exactly how one chunk shipped ~53 s of noise to whisper and looped the decoder.
  `MERGE_GAP_MS = 700` + `PAD_MS = 300` fuse dense runs wall-to-wall, and `extractVoiced` concatenates
  unrelated regions seamlessly — itself a known repetition trigger.
- Improvements (source-level, in order of leverage): (1) noise-floor ceiling — if the 20th percentile
  exceeds ~0.02 the chunk is noise-dominated; re-derive the threshold from the median × 1.5 or raise the
  SNR factor to ~4; (2) voiced-ratio cap — `Voiced.ratioOf()` exists with **zero callers**; above ~0.6,
  re-gate stricter instead of shipping a minute of noise; (3) accumulate zero-crossings in the existing
  per-frame RMS loop and require speech-band ZCR; (4) insert ~200 ms of zeros between regions in
  `extractVoiced` (accounting for offsets) or cap audio per whisper invocation at ≤30 s voiced;
  (5) shrink `MERGE_GAP_MS` toward ~300 ms when frame-voiced ratio is high. Constants need an A/B on the
  saved noisy chunk.

### [P1][data loss] `MIN_SPEECH_RATIO` is relative to chunk length — one short sentence in a 10-minute chunk is deleted as silent
- Where: `VoiceActivityDetector.kt:31, 44–50`; `TranscriptionPipeline.kt:353–370`.
- Problem: the silence gate is `ratio ≥ 0.02` — 12 seconds of speech required in a 10-minute chunk. A lone
  5 s sentence → ratio ≈ 0.008 → SILENT → **WAV released**, with `skipSilentChunks` defaulting on. The
  `wordCount > 0` veto only protects chunks already transcribed once; first-pass chunks are unprotected.
  Mild at the device's current 1-minute chunks (1.2 s bar); becomes real data loss exactly when the app
  moves to its spec'd 10-minute chunks.
- Improvement: key "silent" off `extractVoiced` producing no region (the min-run/merge logic already
  encodes "real utterance") — the `voiced.isEmpty → commitSilent` branch already exists, so the
  `analyse()`-ratio short-circuit can simply be deleted; or add an absolute floor
  (`voicedFrames × FRAME_MS ≥ 2 s`).

### [P1][data loss] `reconcileOrphanAudio` can unlink the live chunk's WAV — the file is created before its DB row
- Where: `AudioChunker.kt:225–231` (`WavWriter(file)` before `onChunkStarted` insert),
  `TranscriptionPipeline.kt:1001–1010`. SYSTEM_DESIGN itself flags the race as "NOT ENFORCED" (I12).
  `beginCapture()` and `pipeline.start()` run back-to-back on every service start, so the orphan sweep
  races the writer opening chunk 1, 24/7. Unlinking an open file succeeds silently on Android — the chunk
  "closes" fine and transcription later finds nothing ("audio file missing").
- Improvement: insert the row before creating the file (swap two lines in `openChunk`), or make the sweep
  skip `.wav` files younger than `chunkMinutes + 5` min — the same cutoff `recoverAbandonedRecording`
  already uses for the same reason.

### [P1][correctness] Crash-orphaned RECORDING rows stay invisible until the *next* process death
- The recorder-side confirmation of §C/D2 — see that entry. Fix is two lines: run
  `recoverAbandonedRecording()` on the `sweepStaleClaims` cadence.

### [P1][robustness] No dead-man signal: when recording should be on but isn't, only the boot path says so
- Where: `RecordingService.kt:337–342` (promotion failure → `stopSelf()`, no notification), `:80–115`
  (the 23:00 summary-only wake generates the summary and shuts down even when `recordingEnabled` is true —
  the system *knows* recording died and says nothing); `BootReceiver.kt:40–52` already builds the correct
  "Echo is not listening — tap to resume" notification.
- Improvement: one helper, three call sites — post the existing `ID_RESUME` notification from every wake
  point that cannot legally capture (promotion failure, summary-only path, `EchoApp.onCreate`).

### [P1][battery] The partial wakelock is held through pauses that can last days; the battery-exemption flow is missing
- Where: `RecordingService.kt:150, 224–242, 257–272, 348–360`; manifest declares
  `REQUEST_IGNORE_BATTERY_OPTIMIZATIONS` but **no code references battery optimisation** (the current
  exemption was granted by hand and dies with a reinstall). Disk-pause ("Storage almost full") and
  `scheduleRestart` keep the CPU pinned while waiting hours-to-days for the user.
- Improvement: release the wakelock in the disk-pause branch and `scheduleRestart` (it is re-acquired by
  `beginCapture` on resume); add a one-time `isIgnoringBatteryOptimizations` check + system prompt in
  settings/onboarding.

### P2 findings
- **`AudioChunker.stop()` self-joins from its own callback threads** (`AudioChunker.kt:143–157` called from
  `onCaptureLost`/`onFatalError`): every capture-loss recovery burns a guaranteed 3 s (reader) or 10 s
  (writer) blocked in the callback before the retry timer starts, with the `AudioRecord` still unreleased.
  Skip the self-join, or hop `scheduleRestart` off the callback thread.
- **The 500 ms progress loop runs 24/7 and never exits on shutdown** (`RecordingService.kt:295–301` — no
  `stopping` check, unlike its sibling); reader wakes 4×/s (`BUFFER_SAMPLES = 4096` → 256 ms reads). Gate
  the poll on `busy`, add the check, and raise the buffer to ~1 s reads.
- **"Listening" is claimed before any audio has arrived** (`RecordingService.kt:211–217` — `isRunning` is
  true the moment threads spawn; `restartAttempt = 0` fires on a possibly-silenced session). Move backoff
  reset + "Listening" to a first-real-frame callback; show "Starting" until then.

### P3 findings
- Notification labels parked chunks "transcribing N" during outages (`RecordingService.kt:283–289`) —
  split parked vs ready counts.
- `WavWriter.write` allocates a fresh ByteBuffer per 256 ms write (~2.7 GB/day of GC churn) — one reusable
  scratch buffer.
- `runBlocking` DataStore reads on the main thread in `onStartCommand`/`beginCapture`
  (`RecordingService.kt:104, 152`) — inside the 5 s `startForeground` window; cache Settings or move off-main.

**Solid:** chunk rotation is genuinely gapless by construction (`AudioRecord` never stopped; `ChunkMath.splits`
sums exactly; unit-tested); WAV crash-safety is well designed end to end (header patch, `repairIfTruncated`,
streaming reads); `AudioGain` matches its A/B'd spec exactly (99.5th-pctile headroom, 12× cap, clamp);
`BootReceiver` is the correct modern-Android design (no illegal mic-FGS start from boot, honest tap-to-resume
notification, correct FGS types/permissions for API 34–36); disk hysteresis is coherent (1.0/1.5 GB band vs
19 MB chunks, single `DiskSpace` source of truth, fails safe).

## E. Transcription pipeline & on-device STT

### [P1][robustness] A service restart steals the previous loop's still-live claim
- Where: `TranscriptionPipeline.kt:155–198` (`stop()` is fire-and-forget — `job?.cancel()`, no join;
  `start()` immediately runs `requeueStale(clock())` under the comment "nothing from a previous process
  can still be holding one"). That assumption holds at process birth only: `pipeline.start` runs on every
  `onStartCommand` in the *same* process, and `job.cancel()` cannot preempt a worker blocked inside
  `whisper_full` (abort lands between ggml graph evaluations; the `NonCancellable deferChunk` hand-back
  runs after that).
- Problem: in the window, the new loop's cutoff-`now` sweep requeues the live claim (+1
  `abandonedClaims`), re-claims the same chunk, and re-transcribes it while the old worker drains —
  double whisper work, two loops sharing `_state`/`cloud`/`lastStaleSweep`, and three quick record
  toggles mid-chunk retire a healthy chunk as crash-looping (`MAX_ABANDONED_CLAIMS = 3`). The lease math
  itself survives (terminal writes are lease-conditional; the ghost's writes are discarded) — though the
  token is a millisecond timestamp, not a nonce.
- Improvement: `start()` captures the previous `Job` and `prev?.join()`s as the first statement of the
  new coroutine; gate the cutoff-`now` sweep behind a once-per-process flag (later starts rely on the
  45-min stale sweep). One change removes the whole two-loop hazard.

### [P1][battery/throughput] Every park cycle pays the full decode before the gate is consulted (§C/D4, quantified)
- `transcribeChunk` runs read → VAD → extractVoiced → normalize unconditionally; only then does
  `runBackends` consult `gate.blockedReason` or learn another chunk holds the server's only worker. A
  parked chunk re-claims every 12–60 s: during an outage that is ~60–80 MB of allocations (19 MB file
  read + 38 MB float array + copies) and a full VAD pass ~4×/min for zero progress — and during a normal
  backlog drain, every 12 s park of the in-flight chunk lets the *next* chunk get fully decoded, VAD'd
  and health-probed just to park on "another chunk is holding the server's only worker".
- Improvement: run the cheap prechecks (gate + `outstandingChunkId`) before touching the file when
  `usesCloud && !underPressure`; also move the outstanding check in `CloudTranscriber.run` ahead of
  `awaken()` so a doomed round doesn't cost a health request.

### [P1][transcript quality] The keep-audio pressure latch, independently confirmed (§G) — with one addition
- Same mechanism as §G's P1 (cap counts USER_REQUEST, valve trades only DEGRADED; ~52 ten-minute chunks
  cross 1 GB and never come back; every network blip then grinds through Whisper at 0.00 Marathi recall,
  unredoable). Addition: consider recording an under-pressure device transcript as DEGRADED even when
  keep-audio is on — both facts are true, the hold column stores one, and the redo-relevant one is
  DEGRADED (the settings flag already protects the file at release time).

### [P1][stuck queue] ModelManager accepts a 90 %-complete model forever, then wedges the pipeline in a 10 s retry loop
- Where: `ModelManager.kt:80–83` (`isInstalled`: `length() > bytes * 0.9`), `:183` (same 90 % test before
  rename), `:142–198` (no `Range` resume, no checksum); `TranscriptionPipeline.kt:234–246` (load failure
  → `delay(10_000)`, forever).
- Problem: a stream that ends cleanly at 90–99 % is renamed into place and counts installed; whisper's
  GGML loader rejects it; `processNext` retries `engine.load` every 10 s indefinitely — heavy mmap I/O,
  queue stalled, UI still showing the model installed. Separately: a 190 MB download restarts from byte
  zero on every drop, with no metered-network warning, and `download()` is not re-entrant.
- Improvement: exact-size equality (sizes are already constants) + pinned SHA-256; `Range` resume against
  the `.part`; on N consecutive load failures quarantine the file so `isInstalled` turns false and the UI
  offers re-download.

### [P1][data loss] `reconcileOrphanAudio` vs the live WAV, independently confirmed (§D) — with one addition
- The window is wider than the millisecond it looks like: the chunker's `runBlocking` row insert queues
  behind the pipeline's own startup-recovery writes on Room's serialized writer, so the sweep's
  `chunksWithAudio()` snapshot can predate the insert by design, at every service start. Same fix stands
  (age-guard the sweep or insert the row first).

### P2 findings
- **The queue drains only while the recording service lives, and the 23:00 summary wake deliberately
  skips the pipeline** (`RecordingService.kt:100–122`; no WorkManager anywhere): turn recording off for
  the evening and the backlog freezes; the summary wake then summarises over the un-drained queue and
  exits. Converges with §G/§H; fix in the summary-only path (`pipeline.start` — it is already a dataSync
  FGS and the loop stops itself when nothing is claimable) and/or an expedited WorkManager drain job.
- **Whole-chunk server rejection with no on-device model is an infinite re-upload loop**: `Rejected` →
  `clearForChunk` → `!engine.isLoaded` → park "waiting for a transcriber" → next claim re-plans and
  re-uploads the same audio the server already refused, forever, on a possibly-metered radio. When
  `Rejected` lands with no engine, `failChunk` (audio kept behind the retry button) instead of parking.
- **Task #11 answered — decoder repetition at the source**: the temperature ladder *is* capped (0.4 → 3
  rungs) and language *is* constrained; decoder-param tuning has little left. The real lever is the
  Silero VAD that is **fully plumbed end to end and deliberately dark** (JNI `params.vad`,
  `vadModelPath` never assigned, `ensureVad` zero callers) because its A/B showed Hindi recall
  0.385→0.231 with output "echoing the tail of the Hindi initial prompt" — which has a mechanical cause:
  `carry_initial_prompt = true` re-injects the prompt into every window, and Silero empties most windows.
  Plan: (1) filter any segment whose normalised text is a substring/high-overlap match of the **known
  constant** `PROMPTS[resolved]` — prompt-echo is exactly filterable, VAD or not; (2) re-run the Silero
  A/B (optionally with `carry_initial_prompt = false`) and re-measure on IndicSpeechInstrumentedTest;

### P2 findings
- **25 MB request bodies are buffered in RAM before the API-key check** (`vexyl_stt_server.py:589–597`
